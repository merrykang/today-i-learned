# DB 이원화 환경에서 통계 집계 합치기 — 별도 테이블 + 멱등 적재 + 플래그 롤백

- 서비스 인프라가 두 존으로 이원화되면서, 별도 존의 일일 이용 통계를 API로 수집해 기존 존의 일일/월간 통계(메일·화면·월집계)에 합산해야 했음. 그때의 설계 결정들

## 1. 컬럼 추가 vs 별도 테이블 → 별도 테이블

기존 `STAT_DAY`에 출처 구분 컬럼을 추가하는 대신 동일 스키마의 `STAT_DAY_<zone>` 테이블을 신설하고 조회 쿼리에 UNION ALL.

- 두 존의 통계 스키마가 동일해서 UNION ALL 비용이 거의 없음 (통계 테이블이라 행 수도 작음)
- **기존 경로 무변경**: 기존 테이블·적재 로직·제약조건을 전혀 건드리지 않으므로 기존 통계에 대한 회귀 위험이 0. 컬럼 추가 방식이면 기존의 모든 조회 쿼리에 출처 조건(또는 기본값 처리)을 넣어야 하고, 하나라도 빠뜨리면 중복 집계·오집계가 조용히 발생
- **삭제 폭발 반경 분리**: 신규 데이터는 재수집 시 날짜 단위 DELETE+INSERT를 반복하는데, 같은 테이블이면 DELETE 조건에서 출처 컬럼을 빼먹는 순간 기존 원본 통계를 지우는 사고가 됨. 테이블이 다르면 그 사고 자체가 불가능
- **수명주기 분리**: 수집 주기·보정 정책·롤백 단위가 기존 데이터와 다름. 잘못되면 신규 테이블만 TRUNCATE하고 재수집하면 끝
- **빈 테이블 전략**: 개발·스테이징 등 전 환경에 테이블을 만들어 두면(`CREATE TABLE ... LIKE`), 조회 쿼리의 UNION ALL을 환경 분기 없이 전 환경 동일하게 배포할 수 있음 — 빈 테이블 UNION ALL은 공짜

## 2. 멱등 적재: 날짜 단위 DELETE 후 INSERT

- 수집 잡이 같은 날짜를 몇 번 다시 돌아도 결과가 같도록, 한 트랜잭션에서 해당 일자 DELETE 후 INSERT
- 멱등성이 확보되면 "재실행 = 복구 수단"이 됨: 장애 났던 날짜를 그냥 다시 돌리면 끝이라, 보정 로직·운영 대응이 전부 단순해짐

## 3. 누락 보정: 조회 윈도우(lookback window)와 "0건" 판정

- 수집 대상 존의 소스가 단일 인스턴스 배치라, 그쪽 장애 시 특정 날짜가 0건(미수집)으로 비어 있을 수 있음
- 매 실행 시 **최근 7일 중 0건인 날짜를 재수집**해서 누락을 보완. 멱등 적재 덕에 이미 있는 날짜를 다시 수집해도 안전
- 한계를 명시적으로 정함: **7일 내내 0건이면 실제 0건으로 확정**. "미수집 0건"과 "실제 0건"은 데이터만으로 구분이 안 되므로, 윈도우로 타협하고 그 기준을 문서화하는 것이 무한 재시도보다 낫다 (더 엄밀히 하려면 수집 이력 테이블로 성공/실패를 기록해 구분하는 방법도 있음)

## 4. "플래그 off만으로 롤백"의 의미

이 설계의 변경은 전부 **덧셈(additive)** 이다 — 새 테이블, 새 수집 잡, 기존 쿼리에 UNION ALL 한 줄. 그리고 수집 잡만 외부 설정 플래그(예: `stat.enabled=true`)에 걸어 둔다.

- 운영에서 문제가 생기면 **플래그만 off** → 수집이 멈추고, UNION ALL은 "더 이상 늘지 않는(또는 빈) 테이블"을 읽을 뿐이라 합산 결과가 자연스럽게 기존 동작으로 수렴. 코드 재배포도 DDL 롤백도 필요 없음
- 반대로 릴리즈 때는 코드 배포(플래그 off 상태 = 기존과 동일 동작)와 기능 활성화(플래그 on)를 분리할 수 있어, 배포 자체가 무위험이 됨
- Martin Fowler의 feature toggle 분류로는 **ops toggle(kill switch)**: 운영자가 기능을 런타임/설정으로 끌 수 있게 두는 토글. "롤백 계획이 설정 한 줄"인 구조는 릴리즈 협조문 쓸 때도 강력함 — 되돌리는 절차가 짧을수록 반영 승인도 쉬워진다
- 전제 조건: 플래그 off일 때의 동작이 "기존과 완전히 동일"해야 함. 미설정 환경에서 잡이 아예 실행되지 않도록 기본값을 off로 두는 것까지가 세트

## 5. 그 외 설계 포인트

- **잡 간 의존 순서를 스케줄에 반영**: 수집 잡(02:30)이 끝난 뒤 월집계 잡이 돌도록 기존 월집계를 02:00→03:00으로 이동. 잡 사이의 암묵적 의존성은 최소한 실행 시각으로라도 명시해야 함
- **수치 검증은 실데이터로**: 수집 대상 존의 실데이터를 미리 export해 신규 테이블에 넣고, 합산 결과(일일 메일·월집계)를 반영 전후로 대조 — "로직이 맞다"가 아니라 "숫자가 맞다"로 검증
- **off 회귀 테스트**: 플래그 없이 배포한 환경에서 기존 통계·메일이 완전히 동일한지 먼저 확인 — additive 설계의 전제("off = 기존과 동일")를 테스트로 증명
- **집계 쿼리 수정 지점 전수 조사**: 일일 메일, 월집계 INSERT, 관리 화면 조회 등 `STAT_DAY`를 읽는 곳을 전부 찾아 UNION ALL 누락이 없는지 확인. 반영 못 하는 화면(예: 10분 단위 실시간 통계)이 있으면 한계로 운영팀에 공유

교훈: 기존 시스템에 데이터 소스를 합칠 때의 안전장치는 세 겹이다 — 구조는 덧셈으로(별도 테이블+UNION ALL), 적재는 멱등으로(재실행=복구), 활성화는 스위치로(롤백=설정 한 줄). 셋이 모이면 "언제든 되돌릴 수 있는 변경"이 되고, 그게 운영 중인 서비스에 기능을 넣는 가장 싼 보험이다.
